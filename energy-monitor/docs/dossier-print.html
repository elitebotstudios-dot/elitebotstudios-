Smart DC Energy Monitor

Engineering Design and Verification Report

Elite Bot Studios · Project 01 · revision B · 6 November 2026

A low-voltage DC energy monitor built in three layers: a software model verified against reference cases, a native KiCad schematic that passes electrical rule check, and firmware that cross-compiles for an ESP32. The physical prototype has not been built and no measurement of hardware exists.

1. Abstract

This report documents the design of a low-voltage direct-current energy monitor intended to measure bus voltage and load current, derive instantaneous power and integrate energy over time. The work is presented in three independent but mutually verifiable layers.

The software model implements the entire measurement chain — source, load, sensing, analogue-to-digital conversion, sampled power and energy accumulation — and is verified by 67 hand-derived reference assertions and 594 checks against independent constructions. The electrical design is a native KiCad schematic built from official library symbols, passing electrical rule check with zero errors and zero warnings, whose exported netlist agrees with the design file on all 42 pins. The firmware extracts current from the shunt voltage, timestamps each sample, integrates energy with an explicit missing-data policy, and cross-compiles for the ESP32 target using PlatformIO with the Xtensa GCC 14.2.0 toolchain; its arithmetic and its sensor driver pass 98 host checks.

What the project does not have is equally important: no printed circuit board, no assembled prototype, no flashed firmware and no measurement against a reference instrument. No accuracy figure is claimed. The report distinguishes throughout between what has been verified computationally and what remains untested physical work.

2. Objectives

The motivating question is not what an energy monitor displays, but how far that display can be from the truth and which stage put the error there.

A monitor reporting 12.00 W is making a claim about a chain of components. A divider scales voltage; a shunt converts current into a small differential voltage; an amplifier and an ADC convert both into numbers; firmware multiplies them and a clock decides how long to accumulate. Each stage contributes an error the others do not cancel, and several of those errors — gain error, a stale sample, an interval integrated across missing data — are indistinguishable from a real change in the load.

The project therefore has three objectives:

  1. Implement the measurement chain in software so that every stage can be varied and tested in isolation.
  2. Produce an electrically valid hardware design for the same chain, checked by tools rather than by assertion.
  3. Implement firmware whose arithmetic can be tested without hardware, and prove it compiles for the intended target.

The shunt is in series with the load, the sensor measures the load side of it, and the reverse-polarity diode sits upstream of the shunt. That ordering is deliberate: the diode costs headroom, but it cannot corrupt the measurement, and the reported power is what the load actually receives.

5. Mathematical model

Power is computed twice, from the measured voltage and current and from the simulated truth, and both are reported:

P = V · I

Energy is accumulated with the trapezoidal rule over the actual interval between accepted samples:

E_import += ½ (P_prev + P_now) · Δt
E_export += ½ (|P_prev| + |P_now|) · Δt          (negative power)
E_Wh = (E_import − E_export) / 3600

An interval containing a sign change is split at the zero crossing by linear interpolation before integration, so imported and exported energy are each integrated over the region where they apply.

Why trapezoidal. It is exact for constant power and second-order accurate for piecewise-linear power. For a step that straddles one interval it smears the step across that interval; with 1 s sampling the error on a 27 000 J run is 2.5 J, or 0.0093 %. Halving the sample interval quarters that error — a convergence order the independent suite checks directly rather than assuming.

Why actual intervals. The model never assumes uniform spacing. Integrating a constant 18 W profile at deliberately irregular timestamps must produce exactly P · (t_end − t_start); this is asserted to 1e-9 J. Summing power samples without multiplying by time is dimensionally wrong, and at 0.5 s sampling it is out by a factor of two.

Sensing chain, per channel, in signal order:

pin  = value · S · (1 + g) + Vos + n        sensitivity, gain error, offset, noise
pin' = clamp(pin, 0, Vref)                  saturation, flagged
code = round(pin' / LSB),  LSB = Vref / 2^bits
reported = code · LSB / S                   uncalibrated
reported = (code · LSB − Vos,est) / (S · (1 + g_est))   calibrated

Calibration is per channel: a divider and a shunt amplifier have independent tolerances, and one correction cannot serve both. An early revision shared a single correction across both channels; the test suite caught it.

Missing data. An invalid sample costs two intervals — the one ending at it and the one starting from it — because the alternative is to integrate across a stale reading. A gap longer than five seconds is treated as missing data and not integrated at all. Both events are counted, so a period with no measurement cannot be mistaken for a period of zero power.

A correction worth recording. Revision A of this design treated the sensor as a breakout module and never modelled VBUS. On the bare IC, VBUS is pin 8, a separate input that must be wired to IN− for load-side measurement; the datasheet's own application example does exactly that. Without it the bus reading comes from the wrong node and every power figure is wrong while appearing plausible. Revision B specifies the bare IC, wires VBUS to VLOAD, straps A0 and A1 to ground for address 0x40, and marks ALERT as an explicit no-connect.

Electrical verification. The schematic is a native KiCad 9 project generated from the design file and built from official library symbols. kicad-cli sch erc reports 0 errors and 0 warnings after two genuine errors were fixed by correcting symbol pin types rather than by disabling the rule. Twenty-five purpose-written design rules additionally check the things ERC cannot: sensor ranges, shunt dissipation and current limit, clamp voltage against the sensor's absolute maximum, connector ratings, ground continuity and measurement polarity.

The split exists so the arithmetic can be tested without a board: the host tests drive the same dcm::Ina226Sensor through a simulated bus that can acknowledge, NACK, report the wrong identity, saturate, over-range or recover.

Two decisions dominate the firmware's behaviour:

  • Current is derived from the shunt voltage and the known resistance, not from the device's current register. This removes any dependence on the calibration register having been written correctly, at the cost of one division per sample.
  • Timestamps are unsigned 32-bit milliseconds, so subtraction wraps correctly after 49.7 days. There is no real-time clock, so no date or time of day is claimed anywhere in the output.

Build. pio run -e esp32dev with PlatformIO 6.2.0, the espressif32 8.0.0 platform and the Xtensa GCC 14.2.0 toolchain produces firmware.bin using 25.4 % of flash and 7.2 % of RAM, with no warnings at -Wall -Wextra. The first attempt failed: setup() and loop() were inside an anonymous namespace, so the Arduino core could never have called them. The binary has never been flashed.

10. Design limitations

  • No hardware accuracy. No sensor, ADC, microcontroller or board was used. Nothing in this report predicts the accuracy of a real implementation.
  • DC only, single channel, non-isolated. No AC, mains, grid or isolation.
  • No switched-mode behaviour. Loads are smooth resistance or current demands; anything faster than the sample interval is aliased.
  • No ADC non-idealities. Quantisation is ideal uniform rounding: no INL, DNL, reference drift or aperture jitter.
  • No MCU behaviour. No fixed-point arithmetic, timer jitter or interrupt latency is modelled.
  • The module question is unresolved. If a breakout module is used instead of the bare IC, its shunt value, pull-up rail, address straps and VBUS connection must be verified physically.
  • ERC is not correctness. It proves the connections are electrically legal, not that the circuit does the right thing.
  • A compile is not a run. The firmware has never executed on hardware.

11. Future physical testing

Seven stages, each with an observable exit condition, defined in verification/calibration-plan/calibration-plan.md and summarised in hardware/design-review/prototype-review-checklist.md:

  1. Review the design and decide bare IC or module.
  2. Identify the parts: markings, shunt resistance, module pull-up rail, VBUS.
  3. Unpowered continuity; prove no short from the protected rail to ground.
  4. First power-up at 5 V and 100 mA with no load.
  5. Communication: I²C scan finds 0x40, identity registers read correctly.
  6. Known loads, compared with a multimeter.
  7. Six-point reference comparison, then calibration, then a repeat.
  8. Uncertainty statement: residual error at each point, repeatability and conditions.

Only after stage 8 does this project have an accuracy figure to publish. Until then the website states the accuracy targets as targets, with no evidence.
